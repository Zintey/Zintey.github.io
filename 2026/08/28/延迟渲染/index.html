    Learn OpenGL 对应章节

    与 延迟渲染（Deferred Rendering） 相对的是 正向渲染（Forward Rendering）。

    正向渲染（Forward Rendering）

    正向渲染的流程是，在光栅化得到片段之后，直接进行光照计算，并通过深度测试决定最终哪些片段能够写入帧缓冲。

    简单来说，每个片段都需要执行一次着色，而着色过程中还需要遍历场景中的灯光。因此，当场景中灯光数量比较多时，就会出现大量重复计算。

    主要有两个问题：

    1. 很多片段虽然执行了完整的着色和光照计算，但最终因为深度测试失败，被后面的片段覆盖掉了，这部分计算就浪费了。
    2. 即使某个灯光根本照不到当前片段，也可能仍然会参与光照计算。

    这也就导致正向渲染在渲染大量光源时，性能会随着灯光数量增加而明显下降。

    延迟渲染（Deferred Rendering）

    为了减少正向渲染中不必要的光照计算，我们可以把光照计算从几何渲染阶段拿出来，延迟到几何信息确定之后再进行，这就是延迟渲染。

    延迟渲染一般可以分成两个阶段：

    1. 几何阶段（Geometry Pass）
    2. 光照阶段（Lighting Pass）

    在几何阶段，我们正常渲染场景中的模型，但这个阶段不进行最终的光照计算，而是把后面光照计算需要的数据写入多个纹理中。这些纹理组合起来，就叫做 G-Buffer（Geometry Buffer）。

    例如，我们可以把：

    • 世界空间位置（Position）
    • 法线（Normal）
    • 漫反射颜色（Albedo）
    • 高光强度（Specular）

    分别保存到不同的纹理中。

    完成几何阶段之后，G-Buffer 中保存的就是当前屏幕上最终可见片段所需要的几何信息。

    然后进入光照阶段，我们读取 G-Buffer 中的数据进行光照计算。

    这样做最大的好处就是：光照计算不再和模型的三角形数量直接绑定，而是和屏幕上的像素数量绑定。

    例如，一个模型即使有很多三角形，但最终只有一部分出现在屏幕上，那么光照阶段只需要对屏幕上的这些像素进行计算。

    当然，延迟渲染也不是没有代价。

    首先，我们需要额外的显存保存 G-Buffer。其次，G-Buffer 通常需要多个纹理，每个屏幕像素可能需要保存几十个字节甚至更多的数据，这会带来比较大的显存带宽压力。

    所以延迟渲染本质上也是一种空间换时间的方案。在灯光数量比较少、场景比较简单的情况下，正向渲染未必会比延迟渲染慢。

    G-Buffer

    G-Buffer 就是在延迟渲染过程中保存几何信息的一组缓冲区。

    这里有一个地方需要特别说明：G-Buffer 并不是在“深度测试过程中”单独记录数据，而是在 Geometry Pass 中，通过片段着色器把当前通过光栅化和深度测试的片段数据写入多个颜色附件。

    如果后面的片段通过深度测试并覆盖了之前的片段，那么对应位置的 G-Buffer 数据也会被新的片段覆盖。

    至于 G-Buffer 里面保存什么数据，没有固定要求，主要取决于后面的光照计算需要什么。

    例如本文中需要：

    • Position：片段的世界空间位置
    • Normal：片段的世界空间法线
    • Albedo：漫反射颜色
    • Specular：高光强度

    如果后面的计算还需要其他数据，也可以继续增加，例如：

    • Roughness
    • Metallic
    • Emissive
    • Ambient Occlusion
    • Material ID

    在 OpenGL 中，我们可以创建一个帧缓冲对象（Framebuffer Object）作为 G-Buffer：

    unsigned int gBuffer;
glGenFramebuffers(1, &gBuffer);
glBindFramebuffer(GL_FRAMEBUFFER, gBuffer);

    然后在这个帧缓冲上绑定我们需要的几何数据。

    这里使用 Texture 来存储 G-Buffer，因为后面的 Lighting Pass 需要通过采样器读取这些数据。

    Position 和 Normal 都是 vec3，所以这里使用 RGB 三个通道保存。

    Albedo 是 RGB 三个通道，Specular 只需要一个通道，因此可以把它们放到同一个 RGBA 纹理中：

    unsigned int gPosition, gNormal, gAlbedoSpec;
glGenTextures(1, &gPosition);
glBindTexture(GL_TEXTURE_2D, gPosition);
glTexImage2D(GL_TEXTURE_2D, 0, GL_RGB16F, screenWidth, screenHeight, 0, GL_RGB, GL_FLOAT, NULL);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MIN_FILTER, GL_NEAREST);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAG_FILTER, GL_NEAREST);
glFramebufferTexture2D(GL_FRAMEBUFFER, GL_COLOR_ATTACHMENT0, GL_TEXTURE_2D, gPosition, 0);

glGenTextures(1, &gNormal);
glBindTexture(GL_TEXTURE_2D, gNormal);
glTexImage2D(GL_TEXTURE_2D, 0, GL_RGB16F, screenWidth, screenHeight, 0, GL_RGB, GL_FLOAT, NULL);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MIN_FILTER, GL_NEAREST);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAG_FILTER, GL_NEAREST);
glFramebufferTexture2D(GL_FRAMEBUFFER, GL_COLOR_ATTACHMENT1, GL_TEXTURE_2D, gNormal, 0);

glGenTextures(1, &gAlbedoSpec);
glBindTexture(GL_TEXTURE_2D, gAlbedoSpec);
glTexImage2D(GL_TEXTURE_2D, 0, GL_RGBA, screenWidth, screenHeight, 0, GL_RGBA, GL_UNSIGNED_BYTE, NULL);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MIN_FILTER, GL_NEAREST);
glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAG_FILTER, GL_NEAREST);
glFramebufferTexture2D(GL_FRAMEBUFFER, GL_COLOR_ATTACHMENT2, GL_TEXTURE_2D, gAlbedoSpec, 0);

unsigned int attachments[3] = { GL_COLOR_ATTACHMENT0, GL_COLOR_ATTACHMENT1, GL_COLOR_ATTACHMENT2};
glDrawBuffers(3, attachments);

    这里需要注意 GL_COLOR_ATTACHMENT0/1/2 和 Shader 中 layout (location = 0/1/2) out 是对应的。

    另外，G-Buffer 仍然需要深度缓冲，用于 Geometry Pass 中正常进行深度测试：

        unsigned int rboDepth;
    glGenRenderbuffers(1, &rboDepth);
    glBindRenderbuffer(GL_RENDERBUFFER, rboDepth);
    glRenderbufferStorage(GL_RENDERBUFFER, GL_DEPTH_COMPONENT, screenWidth, screenHeight);
    glFramebufferRenderbuffer(GL_FRAMEBUFFER, GL_DEPTH_ATTACHMENT, GL_RENDERBUFFER, rboDepth);

    这里使用 Renderbuffer 保存深度数据，是因为后面的 Lighting Pass 并不一定需要直接采样这个深度缓冲。

    最后别忘了检查 Framebuffer 是否完整：

    if (glCheckFramebufferStatus(GL_FRAMEBUFFER) != GL_FRAMEBUFFER_COMPLETE)
    std::cout << "Framebuffer not complete!" << std::endl;

    Geometry Pass

    准备好 G-Buffer 之后，Geometry Pass 就比较简单了。

    Vertex Shader 还是正常完成模型、观察、投影变换，同时把 Position、Normal、UV 传给 Fragment Shader。

    // get_Gbuffer.vert
#version 330 core

layout (location = 0) in vec3 aPos;
layout (location = 1) in vec3 aNorm;
layout (location = 2) in vec2 aUVs;
layout (location = 3) in mat4 aInstanceMatrix; // 这个是为了渲染大量相同模型而传入的实例化 model 矩阵。
					     // 如果想了解实例化，可以看往期文章。

out vec2 UVs;
out vec3 FragPos;
out vec3 Normal;

uniform mat4 view;
uniform mat4 projection;

void main()
{
    UVs = aUVs;

    mat4 model = aInstanceMatrix;

    Normal = mat3(transpose(inverse(model))) * aNorm;
    FragPos = vec3(model * vec4(aPos, 1.0));

    gl_Position = projection * view * model * vec4(aPos, 1.0);
}

    Fragment Shader 不再计算光照，而是把后面需要的数据直接写入 G-Buffer：

    // get_Gbuffer.frag
#version 330 core

layout (location = 0) out vec3 gPosition;
layout (location = 1) out vec3 gNormal;
layout (location = 2) out vec4 gAlbedoSpec;
// 这里的 location 对应 cpp 中的
// GL_COLOR_ATTACHMENT0/1/2

in vec2 UVs;
in vec3 FragPos;
in vec3 Normal;

struct Material {
    sampler2D texture_diffuse1;
    sampler2D texture_specular1;
};

uniform Material material;

void main()
{
    gPosition = FragPos;
    gNormal = normalize(Normal);

    gAlbedoSpec.rgb = texture(material.texture_diffuse1, UVs).rgb;

    gAlbedoSpec.a = texture(material.texture_specular1, UVs).r;
}

    可以看到，这里已经没有任何灯光计算。

    Lighting Pass

    延迟渲染具体的光照计算其实和正向渲染没有本质区别。

    最大的区别是：

    正向渲染从模型的 Fragment Shader 中直接获取 Position、Normal、Albedo 等数据；
    延迟渲染则从 G-Buffer 中读取这些数据。

    因为 G-Buffer 已经保存了屏幕上每个像素对应的几何信息，所以 Lighting Pass 不需要再次渲染场景中的模型。

    最简单的做法就是渲染一个覆盖整个屏幕的面片。

    为什么要渲染一个面片？

    因为这个阶段已经不需要重新进行几何渲染了。我们只关心屏幕上的每一个像素，然后通过 UV 坐标去 G-Buffer 中读取对应位置的数据。

    例如：

    #version 330 core

out vec4 FragColor;

in vec2 UVs;

uniform sampler2D gPosition;
uniform sampler2D gNormal;
uniform sampler2D gAlbedoSpec;

void main()
{
    vec3 color = vec3(0.0);
    vec3 FragPos = texture(gPosition, UVs).rgb;
    vec3 Normal = texture(gNormal, UVs).rgb;
    vec3 Albedo = texture(gAlbedoSpec, UVs).rgb;
    float Spec = texture(gAlbedoSpec, UVs).a;

    for (int i = 0; i < enable_light_cnt; i++)
    {
        if (use_sample_light_volume)
        {
            float dis = length(light[i].position - FragPos);
            if (dis > light[i].radius)
                continue;
        }

        color += calcLight(light[i], FragPos, Normal, Albedo, Spec);
    }

    FragColor = vec4(color, 1.0);
}

    这里的 calcLight() 和正向渲染中的光照计算基本一致。

    因此，延迟渲染并不是改变了光照模型，而是改变了光照计算发生的位置和时机。

    原因也比较直观。

    正向渲染中，光照计算发生在模型的 Fragment Shader 中，场景中有多少个可见片段，就要进行多少次对应的灯光计算。

    而延迟渲染中，Geometry Pass 只负责生成 G-Buffer，Lighting Pass 再针对最终屏幕上的像素进行光照计算。

    因此，灯光数量越多，延迟渲染节省下来的无效光照计算就越明显。

    延迟渲染和正向渲染相结合

    上面讲的延迟渲染，如果要把灯光，也就是 light cube 可视化的话，会出现一些问题。

    light cube 本身也是一个模型，如果我们在 Geometry Pass 中直接渲染它，那么它也会参与 G-Buffer 的生成。

    这样会导致 G-Buffer 中出现 light cube 的数据，而我们后面的 Lighting Pass 是把 G-Buffer 当作场景中最终可见的几何数据来使用的，所以 light cube 就会污染 G-Buffer。

    因此，light cube 不应该参与 Geometry Pass，而是应该在延迟渲染完成之后，再使用正向渲染的方式单独渲染。

    也就是说，场景中的普通模型使用 Deferred Rendering，而 light cube 使用 Forward Rendering。

    不过这里又会遇到另外一个问题。

    Light Cube 的深度问题

    我们的 G-Buffer 有自己的深度缓冲。

    在 Geometry Pass 中，场景模型会正常进行深度测试，所以 G-Buffer 中的深度信息实际上记录了当前场景最终可见的深度。

    但是 Lighting Pass 最终是渲染到默认帧缓冲的，默认帧缓冲并没有自动拥有 G-Buffer 中的深度信息。

    如果这个时候直接把 light cube 渲染到默认帧缓冲中，它进行深度测试时使用的就不是 Geometry Pass 中的深度。

    这样就会出现 light cube 穿过模型或者显示在模型前面的情况。

    下面是没有处理深度信息时的效果：

    可以看到，虽然 light cube 实际上应该被模型挡住，但是因为默认帧缓冲中的深度信息和 G-Buffer 不一致，深度测试没有按照场景原本的深度进行。

    解决这个问题的方法也比较简单。

    在渲染 light cube 之前，把 G-Buffer 中的深度缓冲复制到默认帧缓冲。

    OpenGL 提供了 glBlitFramebuffer 来完成这个操作：

    glBindFramebuffer(GL_READ_FRAMEBUFFER, gBuffer);
glBindFramebuffer(GL_DRAW_FRAMEBUFFER, 0);
glBlitFramebuffer(0, 0, screenWidth, screenHeight, 0, 0, screenWidth, screenHeight, GL_DEPTH_BUFFER_BIT, GL_NEAREST);
glBindFramebuffer(GL_FRAMEBUFFER, 0);

    这里把 gBuffer 作为读取源，把默认帧缓冲作为目标，只复制 GL_DEPTH_BUFFER_BIT。

    这样默认帧缓冲中就拥有了 Geometry Pass 得到的深度信息。

    接下来再正常开启深度测试，渲染 light cube，就可以得到正确的遮挡关系。

    所以这里实际上就是把 Deferred Rendering 和 Forward Rendering 放到了同一个渲染流程中。

    Geometry Pass 负责生成场景的 G-Buffer，Lighting Pass 负责计算不透明物体的光照，最后再使用 Forward Rendering 渲染 light cube 等不需要写入 G-Buffer 的物体。

    结合延迟渲染与正向渲染 cpp 代码

    不过到这里，我们的延迟渲染还有一个比较明显的问题。

    虽然已经把光照计算从 Geometry Pass 中拿了出来，但是在 Lighting Pass 中，我们还是需要遍历所有灯光。

    for (int i = 0; i < enable_light_cnt; i++)
{
    ...
}

    假设现在场景中有 1000 个灯光，那么一个像素还是需要检查 1000 个灯光。

    实际上，一个点光源不可能影响整个场景。

    例如一个灯光的影响半径只有 10，那么距离这个灯光超过 10 的片段，根本不需要计算这个灯光。

    因此，我们可以进一步限制每个灯光影响的像素范围。

    这就是 Light Volume（光体积）。

    光体积（Light Volume）

    所谓光体积，就是一个灯光实际能够影响到的空间范围。

    以点光源为例，我们可以给它设置一个半径，例如半径为 10，那么距离灯光位置超过 10 的片段，就可以直接认为这个灯光不会产生影响。

    因此，对于点光源来说，我们可以直接使用一个球体来表示它的影响范围。

    这个球体本身并不是为了显示出来，而是为了利用它的几何范围来确定当前灯光影响哪些像素。


    例如现在有一个点光源，它的半径为 10，那么我们就创建一个半径为 10 的球体。

    渲染这个球体时，球体覆盖到的屏幕区域，就是这个灯光可能影响到的区域。

    然后在这个区域内读取 G-Buffer，并计算当前灯光的光照。

    这样就不需要让整个屏幕都参与这个灯光的计算。

    这里需要注意，光体积并不一定要使用球体。

    对于点光源，球体比较合适，因为点光源向四周均匀发光，影响范围可以近似看成一个球体。

    如果是聚光灯，那么光体积更适合使用一个锥体。

    所以光体积的形状主要取决于灯光本身的类型和影响范围。

    生成光体积球

    为了渲染点光源的光体积，我们首先需要一个球模型。

    这个球模型可以直接从外部导入，例如使用一个普通的 Sphere 模型即可。

    这里为了避免额外的模型资源，我直接在程序中生成一个球体。

    球体的生成方式比较简单，就是按照经纬度把球面划分成很多小块，然后生成对应的顶点和索引。

    这里的 X_SEGMENTS 和 Y_SEGMENTS 控制球体的精度。

    unsigned int sphereVAO = 0;
unsigned int sphereVBO = 0;
unsigned int sphereEBO = 0;
unsigned int sphereIndexCount = 0;
void renderSphere()
{
    if (sphereVAO == 0)
    {
        std::vector<float> vertices;
        std::vector<unsigned int> indices;
        const unsigned int X_SEGMENTS = 32;
        const unsigned int Y_SEGMENTS = 16;
        const float PI = 3.14159265359f;

        /*
            生成球顶点
            theta: 0 ~ PI
            phi: 0 ~ 2PI

        */
        for (unsigned int y = 0; y <= Y_SEGMENTS; y++)
        {
            for (unsigned int x = 0; x <= X_SEGMENTS; x++)
            {

                float xSegment = (float)x / (float)X_SEGMENTS;
                float ySegment = (float)y / (float)Y_SEGMENTS;


                float xPos = cos(xSegment * 2.0f * PI) * sin(ySegment * PI);
                float yPos = cos(ySegment * PI);
                float zPos = sin(xSegment * 2.0f * PI) * sin(ySegment * PI);

                // position
                vertices.push_back(xPos);
                vertices.push_back(yPos);
                vertices.push_back(zPos);
                // normal
                vertices.push_back(xPos);
                vertices.push_back(yPos);
                vertices.push_back(zPos);
                // uv
                vertices.push_back(xSegment);
                vertices.push_back(ySegment);
            }
        }

        for (unsigned int y = 0; y < Y_SEGMENTS; y++)
        {
            for (unsigned int x = 0; x < X_SEGMENTS; x++)
            {

                unsigned int a = y * (X_SEGMENTS + 1) + x;
                unsigned int b = (y + 1) * (X_SEGMENTS + 1) + x;
                unsigned int c = (y + 1) * (X_SEGMENTS + 1) + x + 1;
                unsigned int d = y * (X_SEGMENTS + 1) + x + 1;
                indices.push_back(a);
                indices.push_back(d);
                indices.push_back(b);

                indices.push_back(d);
                indices.push_back(c);
                indices.push_back(b);
            }
        }
        sphereIndexCount = indices.size();
        // VAO
        glGenVertexArrays(1, &sphereVAO);
        glBindVertexArray(sphereVAO);
        // VBO
        glGenBuffers(1, &sphereVBO);
        glBindBuffer(GL_ARRAY_BUFFER, sphereVBO);
        glBufferData(GL_ARRAY_BUFFER, vertices.size() * sizeof(float), &vertices[0], GL_STATIC_DRAW);
        // EBO
        glGenBuffers(1, &sphereEBO);
        glBindBuffer(GL_ELEMENT_ARRAY_BUFFER, sphereEBO);
        glBufferData(GL_ELEMENT_ARRAY_BUFFER, indices.size() * sizeof(unsigned int), &indices[0], GL_STATIC_DRAW);

        glEnableVertexAttribArray(0);

        glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 8 * sizeof(float), (void*)0);
        glEnableVertexAttribArray(1);
        
        glVertexAttribPointer(1, 3, GL_FLOAT, GL_FALSE, 8 * sizeof(float), (void*)(3 * sizeof(float)));
        glEnableVertexAttribArray(2);

        glVertexAttribPointer(2, 2, GL_FLOAT, GL_FALSE, 8 * sizeof(float), (void*)(6 * sizeof(float)));
        glBindVertexArray(0);
    }
    // draw sphere
    glBindVertexArray(sphereVAO);

    glDrawElements(GL_TRIANGLES, sphereIndexCount, GL_UNSIGNED_INT, 0);
    glBindVertexArray(0);
}

    这里生成的球体半径是 1。

    真正渲染某一个灯光的光体积时，只需要根据这个灯光的半径对球体进行缩放，再移动到灯光的位置即可。

    例如灯光半径是 10，那么最终渲染出来的球体就是半径为 10 的光体积。

    光体积的渲染

    有了球体之后，接下来就是怎么利用它来减少光照计算。

    这里需要稍微改变一下之前 Lighting Pass 的思路。

    之前我们是渲染一个覆盖整个屏幕的面片，然后在 Fragment Shader 中遍历所有灯光。

    现在则变成了：

    每一个灯光单独渲染自己的光体积。

    例如当前正在处理第 i 个灯光，就把球体移动到这个灯光的位置，并按照灯光半径进行缩放。

    然后只渲染这个球体。

    球体没有覆盖到的屏幕区域，就不会执行这个灯光对应的 Fragment Shader。

    这样就可以天然地把灯光计算限制在光体积范围内。

    在 Fragment Shader 中，Position、Normal、Albedo、Specular 这些数据仍然是从 G-Buffer 中读取。

    真正改变的是光照计算的范围。

    之前：

    for (int i = 0; i < enable_light_cnt; i++)
{
    color += calcLight(light[i], FragPos, Normal, Albedo, Spec);
}

    现在不再需要在一个 Shader 中遍历所有灯光。

    当前渲染的是哪个光体积，就只计算对应的那个灯光：

    color += calcLight(light, FragPos, Normal, Albedo, Spec);

    然后通过混合，把多个灯光的结果累加到最终颜色中。

    这里通常需要开启颜色混合：

    glEnable(GL_BLEND);
glBlendFunc(GL_ONE, GL_ONE);

    这样每个灯光计算出来的颜色就可以直接累加到之前的结果上。

    光体积还有一个比较重要的地方，就是它本身会经过深度测试。

    对于完全位于模型后面的光体积区域，我们不需要进行光照计算。

    因此，光体积渲染实际上还需要结合深度测试和面剔除来减少不必要的 Fragment Shader 执行。

    具体的实现方式和光体积与摄像机的位置关系有关，这里使用的实现可以直接参考上面的代码。

    光体积性能测试

    前面我们已经测试过正向渲染和普通延迟渲染。

    现在继续测试加入光体积之后的效果。

    测试场景保持不变，仍然是 1000 个模型，每个模型大约 6000 个面。

    100 个灯光。

    使用光体积之后，灯光半径设置为 10，帧率提升到了大约 95 FPS：

    500 个灯光：
    帧率大约为 65 FPS。

    1000 个灯光：

    帧率大约为 45 FPS。

    2000 个灯光：

    帧率大约为 30 FPS。

    从这个测试可以看到，普通延迟渲染虽然已经比正向渲染好很多，但是它仍然需要让每个像素检查所有灯光。
    光体积进一步把这个范围缩小到了每个灯光实际影响到的屏幕区域。
    在灯光数量不断增加的情况下，这个优化就比较明显了。

    当然，光体积也不是灯光越多性能就越好。灯光数量达到一定程度之后，渲染光体积本身也会带来越来越多的 Draw Call 和几何处理开销。

    尤其是当大量光体积在屏幕上互相重叠时，同一个像素仍然可能需要执行很多次光照计算。

    所以光体积主要解决的是：

    避免一个灯光对完全不可能受到它影响的像素进行光照计算。

    对于本文的测试场景，灯光半径固定为 10，随着灯光数量增加，光体积之间的重叠也越来越多，因此帧率还是会继续下降。

    但是相比让每个像素直接遍历所有灯光，光体积已经把大量没有意义的计算去掉了。

    到这里，基本就完成了从正向渲染到延迟渲染，再到光体积优化的过程。

    正向渲染中，灯光计算直接发生在模型的 Fragment Shader 中，模型有多少可见片段，就需要进行多少次对应的灯光计算。

    延迟渲染把这个过程拆成了 Geometry Pass 和 Lighting Pass，先把后面需要的数据保存到 G-Buffer，再统一进行光照计算。

    而光体积进一步限制了每个灯光实际需要计算的屏幕范围。

    这几个技术本质上都是在解决同一个问题：

    尽量不要计算那些最终不会影响画面的东西。

    延迟渲染解决的是被遮挡片段的光照计算浪费，光体积则进一步解决灯光影响范围之外的计算浪费。

    当然，随着灯光数量继续增加，单纯使用光体积也会逐渐遇到瓶颈。因为每个灯光仍然需要单独处理，而且多个光体积重叠时，一个像素仍然可能需要计算很多灯光。

    所以后面还可以继续优化，例如把屏幕划分成很多小区域，只记录每个区域中有哪些灯光，再根据当前像素所在的区域去计算对应的灯光。这就是 Tiled Deferred Shading。

    在此基础上，还可以进一步把屏幕空间和深度划分结合起来，也就是 Clustered Shading。

    这些方法本质上都是在继续解决同一个问题：如何更准确地找到“当前像素真正需要计算哪些灯光”，从而避免遍历大量无关的灯光。
