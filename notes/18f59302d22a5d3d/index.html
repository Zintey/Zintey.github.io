    本文主要介绍 UE 的垃圾回收机制（Garbage Collection，简称 GC），包括是什么、具体机制以及怎么用。

    • 是什么
    • 具体机制
    • 怎么用

    是什么

    GC（Garbage Collection，垃圾回收）是一种自动内存管理机制，用来回收程序中不再需要的对象所占用的内存。
    先讲讲普通 C++ 如何管理内存。标准 C++ 本身没有内建的追踪式 GC，通过 new 创建的对象通常需要按所有权规则释放。

    MyClass* p = new MyClass(); // 通过new申请堆内存
...
delete p; // delete释放p指向的内存

    如果每次 new 都需要手动配对 delete，不仅麻烦，还容易因遗漏而造成内存泄漏。
    于是可以采用RAII思想（Resource Acquisition Is Initialization 资源获取即初始化），简单来说，就是将资源的生命周期绑定到对象的生命周期，通过构造函数获取资源，通过析构函数释放资源。（关于RAII更详细的介绍可以看这篇文章）
    下面是利用RAII机制，简单封装的一个类（MyPtr）

    i查看代码
    #include <iostream>
template<typename T>
class MyPtr
{
public:
    MyPtr() { pointer = new T(); }
    ~MyPtr() { delete pointer; }
    MyPtr(const MyPtr&) = delete;
    MyPtr& operator=(const MyPtr&) = delete;
    T* operator->() { return pointer; }
    T& operator*() { return *pointer; }
private:
    T* pointer;
};
class Node {
public:
    Node() { std::cout << "begin" << std::endl; }
    ~Node() { std::cout << "end" << std::endl; }
    void SetData(int d) { data = d; }
    int GetData() { return data; }
private:
    int data;
};
int main()
{
    MyPtr<Node> p;
    p->SetData(10);
    std::cout << p->GetData() << std::endl;
    return 0;
}

    C++ 标准库也提供了智能指针，如 std::unique_ptr、std::shared_ptr 和 std::weak_ptr。其中 unique_ptr 独占所有权，shared_ptr 通过强引用计数管理共享所有权，weak_ptr 不增加强引用计数。shared_ptr 之间如果形成强引用环，就可能无法自动释放对象。
    UE 对 UObject 及其派生类采用了另一套基于可达性分析的 GC 机制，并利用反射信息识别对象引用。通常可以通过 NewObject 创建对象，再由 GC 在后续周期中回收不再可达、且没有其他保活机制的对象。

    具体机制

    UE 的 GC 可以简化理解为“标记—清除”：从根对象等有效引用来源出发，标记可达对象；再将未标记、且符合回收条件的对象交由后续销毁与内存回收流程处理。

    因此，需要一个地方管理所有 UObject，还需要一种机制识别它们之间的引用关系。

    GUObjectArray数组

    先讲讲存放所有对象的地方
    创建 UObject 的一种常见方式是 NewObject，例如 UObject* obj = NewObject<UObject>();。此外还有加载对象、创建默认子对象等途径。
    最终会调用到UObjectBase::AddObject，这个函数如下

    iAddObject
    UE_AUTORTFM_ALWAYS_OPEN
void UObjectBase::AddObject(FName InName, EInternalObjectFlags InSetInternalFlags, int32 InInternalIndex, int32 InSerialNumber, FRemoteObjectId InRemoteId)
{
	new (&NamePrivate) FNameAndObjectHashIndex(InName); // Overwrite potentially compiled-in string
	EInternalObjectFlags InternalFlagsToSet = InSetInternalFlags;
	if (!IsInGameThread())
	{
		InternalFlagsToSet |= EInternalObjectFlags::Async;
	}
	if (ObjectFlags & RF_MarkAsRootSet)
	{		
		InternalFlagsToSet |= EInternalObjectFlags::RootSet;
		ObjectFlags &= ~RF_MarkAsRootSet;
	}
	if (ObjectFlags & RF_MarkAsNative)
	{
		InternalFlagsToSet |= EInternalObjectFlags::Native;
		ObjectFlags &= ~RF_MarkAsNative;
	}
	GUObjectArray.AllocateUObjectIndex(this, InternalFlagsToSet, InInternalIndex, InSerialNumber, InRemoteId);
	check(InName != NAME_None && InternalIndex >= 0);
	HashObject(this);
	check(IsValidLowLevel());
}

    其中GUObjectArray.AllocateUObjectIndex(this, InternalFlagsToSet, InInternalIndex, InSerialNumber, InRemoteId); 将这个UObject对象加到了GUObjectArray数组中
    因此，UObject 及其派生类的实例都会被纳入这套全局对象管理结构（不是说普通 C++ 对象也在其中）。

    可达性分析

    现在我们有了一个存着所有UObject对象的数组，接着需要一种机制来判断哪些对象不可回收
    UE 采用可达性分析的方式，具体是什么可达呢？
    可以先将 RootSet 理解为可达性分析的起点：GC 会沿着能识别的强引用关系继续遍历。实际引擎还存在其他引用来源和保活机制。
    如果一个对象可以从RootSet的一个节点通过一层层的引用到达，则表示它不可回收

    举个例子，假设一个 UMyObject 实例由 GameInstance 持有：

    UCLASS()
class MY_API UMyObject : public UObject
{
    GENERATED_BODY()
public:
    UPROPERTY()
    TObjectPtr<UObject> B;
};

UCLASS()
class MY_API UMyGameInstance : public UGameInstance
{
    GENERATED_BODY()
public:
    virtual void Init() override
    {
        Super::Init();
        A = NewObject<UMyObject>(this);
        A->B = NewObject<UObject>(A);
    }

private:
    UPROPERTY()
    TObjectPtr<UMyObject> A;
};

    这里在 Init() 中创建对象，而不是在 UObject 构造函数里直接调用 NewObject。
    可以先假设 GameInstance 是 GC 的有效起点，并且 A、B 没有其他强引用。

    GC 如何发现对象间的引用

    现在知道了所有UObject对象存放的地方，以及 GC 是怎么判断一个对象不可回收。
    但怎么让 GC 在可达性分析时发现引用关系呢？
    需要有个东西，能记录每个实例都有什么引用，在运行时可以通过这个东西来找到每个实例的引用对象，以此不断递归下去。以RootSet的节点开始递归，就可以标记所有不可回收的节点，完成可达性分析。
    先假设每个实例都保存一个 MemberPtr 数组，记录它的引用，如下伪代码（不是 UE 的实际实现）：

    class Object {
protected:
    std::vector<Object*> MemberPtr;
};

class MyObj : public Object {
    Object* A = nullptr;
    Object* B = nullptr;
public:
    MyObj() {
        MemberPtr.push_back(A);
        MemberPtr.push_back(B);
    }
};

    但这个其实有问题
    （1）我们在构造函数中把所有引用添加到MemberPtr，但如果运行过程中，引用A、B发生了变化，MemberPtr中的值并不会改变
    （2）每次都要在构造函数中把所有需要让GC系统做可达性分析的引用都手动添加一下，很麻烦。

    先解决第一个问题
    要是我们存放A、B的地址，而不是指向的值，那不就解决了吗，比如

    class Object {
protected:
    std::vector<void*> MemberPtr;
};

class MyObj : public Object {
    Object* A = nullptr;
    Object* B = nullptr;
public:
    MyObj() {
        MemberPtr.push_back(&A);
        MemberPtr.push_back(&B);
    }
};

    在使用MemberPtr时在做这样的操作

    for (void* member_address : MemberPtr)
{
	Object* member_ptr = *static_cast<Object**>(member_address);
}

    这样就能在遍历时读到成员 A、B 当前保存的指针值。
    但其实没必要这么麻烦，cpp 有一种特殊的指针，叫类成员指针，它可以描述某个类中的特定成员，而不绑定具体实例。对于简单的数据成员，其底层通常可以用成员偏移量来理解，但 C++ 标准不保证它一定以偏移量存储
    可以用这个类成员指针来替代上面我们自己写的void*指针

    template<typename T>
class Object {
protected:
    std::vector<T* T::*> MemberPtr;
};

class MyObj : public Object<MyObj> {
    MyObj* A = nullptr;
    MyObj* B = nullptr;
public:
    MyObj() {
        MemberPtr.push_back(&MyObj::A);
        MemberPtr.push_back(&MyObj::B);
    }
};

    这里借助奇异递归模板模式（CRTP）让基类模板知道派生类的类型。不过，MemberPtr 仍然只能存储 MyObj* MyObj::* 这一种成员指针，无法直接存储其他成员类型。

    为了支持不同类型的成员，也为了避免每次都手动向 MemberPtr 注册，我们来看看 UE 是怎么实现的。
    UE 通过UE反射系统和一系列宏，标记需要在运行时获取的类及成员信息，例如：

    UCLASS()
class UMyObj : public UObject
{
    GENERATED_BODY()
private:
    UPROPERTY()
    TObjectPtr<UMyObj> A;

    UPROPERTY()
    TObjectPtr<UMyObj> B;
};

    其中：

    • UCLASS() 告诉 UHT，这个类需要生成 UE 反射信息。
    • GENERATED_BODY() 将 UHT 生成的必要 C++ 声明引入类中。
    • UPROPERTY() 告诉 UHT，这个成员需要加入 UE 的反射系统。

    UHT（Unreal Header Tool）会在 C++ 编译前解析这些声明，并生成相应代码。这并不是说宏在运行时遍历、注册每个实例的成员，而是为类生成可复用的属性描述。

    假设用我们自己的简化结构来表示 UHT 产生的信息，可以理解成：

    // 原理伪代码，不是 UE 实际生成的源码
struct MemberInfo
{
    const char* Name;
    size_t Offset;
    MemberType Type;
};

MemberInfo Members[] = {
    {"A", /* A 的偏移量 */, MemberType::ObjectReference},
    {"B", /* B 的偏移量 */, MemberType::ObjectReference}
};

    有了成员名称、类型和位置信息，就能在运行时定位任意实例的对应成员；不同实例可以共用同一份类级别描述。

    UE 实际使用的是 UClass 和 FProperty 等反射类型。UClass 描述类，FProperty 描述成员属性。不同成员由不同属性类型描述，例如 FIntProperty 对应整数、FObjectProperty 等对象属性类型对应 UObject 引用，FArrayProperty 对应数组。

    但反射系统记录了属性，还不代表 GC 会扫描全部属性：GC 只需要关心那些包含 UObject 引用的属性。

    GC Schema

    为了高效遍历对象引用，UE 会根据属性反射信息构建专门用于 GC 的引用描述，称为 GC Schema（引用 Schema）。其中记录了如何从对象内部找到需要追踪的引用，而不只是成员名称。

    相关实现中可以看到 FProperty::EmitReferenceInfo 和 UE::GC::FSchemaBuilder：不同属性根据自身类型生成引用信息，由 Schema Builder 组织成 GC 使用的 Schema。

    可以把它简单理解成：

    // 仅用于说明原理，不是 UE 的真实 Schema 数据结构
struct GCReferenceInfo
{
    size_t Offset;
    ReferenceKind Kind;
};

// 比如：
// A -> 一个 UObject 引用
// Children -> 包含 UObject 引用的数组，需要遍历元素

    因此，对于：

    UPROPERTY()
TObjectPtr<UObject> A;

UPROPERTY()
TArray<TObjectPtr<UObject>> Children;

UPROPERTY()
int32 Data = 0;

    GC 需要处理 A 和 Children 中的引用，但不需要沿着普通整数 Data 继续查找对象。对于数组、结构体等类型，还需要按照对应规则遍历内部元素。

    GC 进行可达性分析时，就可以根据对象所属类的 Schema 找到该实例持有的 UObject 引用，再继续访问这些对象。这样就把前面提到的“对象地址 + 成员定位信息”与实际 GC 的引用遍历联系起来了。

    需要注意，UPROPERTY() 是 GC 发现引用的重要途径，但并不是唯一途径；引擎也提供 AddReferencedObjects、FGCObject 等方式报告引用。

    怎么用

    前面了解了 GC 如何通过 Schema 等信息发现对象引用，实际使用时最重要的就是：让 GC 能发现需要保留的引用；不需要保留对象时，使用弱引用。

    下面按不同场景介绍。以下主要讨论由 UE GC 管理的 UObject 及其派生类，普通 new 出来的 C++ 对象不在这套 GC 管理范围内。

    1. UPROPERTY()：最常见的强引用方式

    如果一个 UObject 要长期持有另一个 UObject，通常直接使用：

    UCLASS()
class UMyObj : public UObject
{
    GENERATED_BODY()

public:
    UPROPERTY()
    TObjectPtr<UObject> Target = nullptr;
};

    只要 UMyObj 实例自身可达，GC 就能通过反射信息发现 Target，并继续追踪它引用的对象。如果 UMyObj 自己已经不可达，那么这个 UPROPERTY() 也无法单独让 Target 存活。

    UPROPERTY() 的作用是把成员加入反射系统，并不是所有标记了 UPROPERTY() 的成员都会形成 GC 强引用。例如 int32 不是对象引用，TWeakObjectPtr 也是弱引用。

    UObject* 和 TObjectPtr 的区别

    这几种写法需要区分：

    // ① 被反射系统识别的裸指针成员（传统写法）
UPROPERTY()
UObject* A = nullptr;

// ② 推荐的 UObject 引用成员写法
UPROPERTY()
TObjectPtr<UObject> B = nullptr;

// ③ 没有 UPROPERTY 的普通裸指针
UObject* C = nullptr;

// ④ 没有 UPROPERTY 的 TObjectPtr
TObjectPtr<UObject> D = nullptr;
    写法 是否能通过该成员形成 GC 强引用
    UPROPERTY() UObject* 在支持此类反射属性的常见 UE 配置中，可以
    UPROPERTY() TObjectPtr<UObject> 可以，UE5 推荐写法
    UObject*（无 UPROPERTY） 不会仅因为这个指针存在而保活对象
    TObjectPtr<UObject>（无 UPROPERTY） 不会仅因为这个成员存在而保活对象

    也就是说，不是把 UObject* 换成 TObjectPtr，GC 就自动能找到这个引用；通常还需要 UPROPERTY() 等 GC 能识别的引用报告机制。

    TObjectPtr 是 UE5 针对 UObject 引用提供的指针封装，除了反射支持，还能配合引擎的增量 GC 使用写屏障等机制。因此在 UE5 中，推荐优先使用 UPROPERTY() TObjectPtr<T> 来声明需要被 GC 追踪的成员。

    普通 UObject* 仍适合函数参数、返回值，以及不会跨越 GC 时机的短期访问；但它本身不提供生命周期保证。

    USTRUCT 和容器中的引用

    UPROPERTY() 也可以用于反射结构体内的属性。对于 GC 能识别的嵌套结构体和 UE 容器，引擎会沿着其属性描述继续寻找引用。

    USTRUCT()
struct FMyData
{
    GENERATED_BODY()

    UPROPERTY()
    TObjectPtr<UObject> Target = nullptr;
};

UCLASS()
class UMyObj : public UObject
{
    GENERATED_BODY()

public:
    UPROPERTY()
    FMyData Data;

    UPROPERTY()
    TArray<TObjectPtr<UObject>> Children;
};

    如果 UMyObj 可达，那么 GC 能根据反射信息继续检查 Data.Target 和 Children 中的引用。这里不能只给最里面的成员加 UPROPERTY()，却让外层容器或结构体完全脱离 GC 的可发现路径。

    2. TStrongObjectPtr：普通 C++ 类中的强引用

    如果持有者不是 UObject，例如普通的 C++ 类，就不能像 UCLASS 一样给它的普通成员使用 UPROPERTY() 来参与 UE 反射。

    此时可以使用 TStrongObjectPtr：

    #include "UObject/StrongObjectPtrTemplates.h"

class FMyManager
{
public:
    TStrongObjectPtr<UObject> Target;

    void Init()
    {
        Target.Reset(NewObject<UObject>());
    }
};

    TStrongObjectPtr 会向 GC 提供强引用，只要这个强引用仍然存在，就能防止目标对象因为不可达而被 GC 回收。它不需要 UPROPERTY()，也不能用 UPROPERTY() 标记。

    例如也可以在局部作用域中使用：

    TStrongObjectPtr<UObject> Target(NewObject<UObject>());
// Target 存活期间，目标对象受到 GC 保护

    不过它不是普通 UObject 成员引用的首选。因为它会独立提供保活引用，滥用容易导致对象迟迟无法回收；创建、销毁这类引用也有成本。在 UObject 成员中，通常还是优先使用 UPROPERTY() TObjectPtr<T>。

    3. AddToRoot()：直接把对象加入根集合

    还有一种方式是直接让对象成为 GC 根：

    UObject* Obj = NewObject<UObject>();
Obj->AddToRoot();

// 使用 Obj ...

Obj->RemoveFromRoot();

    调用 AddToRoot() 后，这个对象会被当作 GC 的根对象，不会因为普通引用消失而被回收；调用 RemoveFromRoot() 后，才重新允许 GC 根据可达性判断它是否能被回收。

    这种方式比较直接，但需要自己管理何时移除根引用。如果忘记 RemoveFromRoot()，就可能让对象长期无法回收。

    因此，不建议把 AddToRoot() 当作日常持有 UObject 的默认方案，只有确实需要显式控制根对象生命周期时再使用。

    4. FGCObject：手动向 GC 报告引用

    如果普通 C++ 类中有多个 UObject 引用，或者需要自定义引用收集逻辑，可以继承 FGCObject，在 AddReferencedObjects 中把需要保留的对象报告给 GC。

    #include "UObject/GCObject.h"

class FMyManager : public FGCObject
{
public:
    UObject* A = nullptr;
    UObject* B = nullptr;

    virtual void AddReferencedObjects(FReferenceCollector& Collector) override
    {
        Collector.AddReferencedObject(A);
        Collector.AddReferencedObject(B);
    }

    virtual FString GetReferencerName() const override
    {
        return TEXT("FMyManager");
    }
};

    只要这个 FGCObject 实例本身仍然有效并已注册到 GC 的引用报告机制中，GC 就可以通过它提供的引用找到 A、B。

    与 TStrongObjectPtr 相比，FGCObject 更适合需要自行收集多个引用的管理类；同时必须保证负责报告引用的 FGCObject 实例生命周期正确。

    此外，UE 还提供 TGCObjectScopeGuard 等作用域辅助工具，可在特定作用域中保护一个或多个对象引用。

    对于 UObject 派生类，引擎还有 AddReferencedObjects(UObject*, FReferenceCollector&) 这类类级别的引用报告入口，可以处理常规属性 Schema 没有覆盖的自定义引用。它与普通 C++ 类使用的 FGCObject 不是同一种继承方式。

    5. 不想阻止 GC 回收：弱引用和软引用

    有时我们只是想记录一个对象，允许它在没有其他强引用时被回收，这时就不应该用强引用保活它。

    例如 TWeakObjectPtr：

    TWeakObjectPtr<UObject> Target;

// 使用前检查
if (UObject* Obj = Target.Get())
{
    // 使用 Obj
}

    弱引用不会阻止 GC 回收目标对象。对象失效后，可以通过 IsValid() 或 Get() 判断，避免继续把悬空地址当成有效对象使用。

    另一种常见类型是 TSoftObjectPtr，主要用于保存资源引用路径，并支持按需加载。它同样不等于 GC 强引用：软引用可以定位或加载资源，但不会仅因为存在软引用就让已加载对象一直存活。

    6. 其他需要注意的情况

    Outer 不等于强引用。

    UObject* Child = NewObject<UObject>(Outer);

    这里指定 Outer，并不等于 Outer 自动对 Child 形成 GC 强引用。Outer 主要参与对象的归属、命名等机制，是否保活仍取决于 GC 能识别的引用关系或其他保活机制。

    AActor / UActorComponent 有自己的生命周期规则。

    它们也属于 UObject 体系，但不能简单地认为“只要存在强引用，Actor 就绝对不能销毁”。例如 AActor::Destroy() 会走 Actor 的销毁流程，不能用普通 UObject 的 GC 规则完全代替 Actor 生命周期管理。

    不要随便对 UObject 使用 delete。

    通常通过 NewObject、SpawnActor 等引擎 API 创建对象，再按对应生命周期机制管理。GC 管理的 UObject 不应该由业务代码直接 delete。

    小结

    场景 通常使用的方式 是否保活目标对象
    UObject 的引用成员 UPROPERTY() TObjectPtr<T> 是，前提是持有者可达
    传统 UObject 裸指针反射属性 UPROPERTY() T* 通常是；UE5 更推荐 TObjectPtr
    普通 C++ 类持有少量 UObject TStrongObjectPtr<T> 是
    普通 C++ 类自行收集多个引用 FGCObject 是，针对主动报告的引用
    显式把对象作为 GC 根 AddToRoot() 是，直到解除根标记
    UObject 自定义引用报告 AddReferencedObjects 是，针对主动报告的引用
    仅观察对象，不负责保活 TWeakObjectPtr<T> 否
    资源路径及按需加载 TSoftObjectPtr<T> 否
    普通成员裸指针、无反射注册 T* 否，除非另有引用来源

    所以在日常开发中
    优先使用 UPROPERTY() TObjectPtr<T> 来声明需要 GC 追踪的 UObject 成员引用；
    普通 C++ 持有者再考虑 TStrongObjectPtr 或 FGCObject；
    需要主动控制根集合时才使用 AddToRoot()。
    而不需要保活对象时，则使用弱引用或软引用。
